## 五鐵律

1. ⛔ **蝴蝶效應**：發現問題當下處理，不處理不繼續。含 pre-existing。處理不了→寫入交接「未解決」段。已硬化 `butterfly_guard.py`
2. ⛔ **交接三態**：✅⏸⬜。半完成用 ⏸（格式：`⏸ 任務 — 已完成：X。待做：Y`）。做完必標狀態。禁止假 ✅
3. ⛔ **驗證至上**：D = 功能驗證。UI→必須截圖。tsc/lint 是前提不算驗證。無法驗→⏸ 延遲
4. ⛔ **沉澱鐵律**：被糾正→① 修正 ② 更新 `kb_*` Skill ③ 更新規則。不沉澱 = 下次重犯
5. ⛔ **反熵優先**：修改持久檔前→讀全檔→刪過期/重複/已硬化→才寫新內容。寫 10 行至少清 5 行等值。預算：交接 ≤300 行 | MEMORY ≤120 行

## 規則治理 SOP（規則的規則）

### 三層定義

| 層 | 位置 | 載入時機 | 預算 | 用途 |
|----|------|----------|------|------|
| **L0** | `rules/00-L0.md` | 每次自動 | ≤350t | 遺忘=災難 **且** 無觸發條件可補救 |
| **L1** | `rules/L1/*.md` | 觸發條件命中時 | 每檔 ≤600t | 有明確觸發條件的操作規則 |
| **L2** | KB Skill / Planning / 交接 | 手動或 Skill 觸發 | 不限 | 參考資料、歷史、詳細規格 |

### 新增規則

1. **預設歸 L1**。要進 L0 必須同時滿足：① 遺忘=災難 ② 沒有觸發條件可補救 ③ 一行能寫完
2. L0 新增前**先檢查是否重複現有規則**。重複→合併，不加新條
3. L0 新增後**必須檢查總 token**。超 350t→必須降級一條到 L1 騰空間
4. L1 新增必須在 L0 觸發表加對應觸發條件
5. **格式統一**：L0 = `⛔ **名稱**：一句話定義`。L1 = 標題 + 分段詳述

### 修改規則

- ⛔ **只有三種合法修改理由**：① 發現錯誤/問題 ② 用戶明確指令 ③ 硬化後歸還注意力（刪）
- ❌ 「改進」「優化」「更清楚」不是修改理由。初衷不飄移
- 修改 L0 時同步檢查：L1 對應檔是否需要連動更新
- 修改 L1 時同步檢查：L0 觸發條件是否仍正確

### 刪除規則

- 已硬化（Guard/Gate 代碼強制）→ **必須刪**，歸還注意力預算
- 過期（專案結束/需求變更）→ 刪除，記錄在交接「歷史」段
- 重複 → 合併到權威位置，刪除副本

### 預算紅線

- **常駐總量 ≤1,500t**（L0 + CLAUDE.md + MEMORY，當前 ~1,230t）
- **L0 ≤600t**（當前 ~510t）— 開頭位置 primacy bias 90%，比 inject 容忍度高
- **MEMORY ≤120 行**（當前 59 行）
- **L1 單檔 ≤600t**
- 超預算 = 先清再加，不是加了再清
