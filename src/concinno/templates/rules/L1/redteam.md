# 重大決策紅藍隊 SOP（L1 按需載入）

I design as blue. Red is always a clean subagent. Self-redteam is theater.

## CBUA vs 紅藍隊 SOP 的層級

**CBUA = 任何問題都跑**（C0 路由 + 五定律，包含 Simple→C1）。
**紅藍隊 SOP = 決策級才跑**（C2/C3 + 不可逆 + 架構級才需要）。

CBUA 是底層認知框架，紅藍隊是上層流程。
做 Simple 任務不需要紅隊，但仍要跑 CBUA C0 路由。

## 紅藍隊 SOP 觸發條件（任一命中 = 強制執行）

- 架構級設計（新模組、新系統、新 pipeline）
- 重寫核心邏輯（>200 行 + 影響其他模組）
- 不可逆決策（DB schema / API 介面 / 開源 release）
- 投入 >1 天的方向性選擇
- 用戶說「重大決策」「重要決定」「不要亂搞」
- ⛔ **模型訓練 / 微調**（花錢花時間且需要業界承認）：訓練前強制全面審視訓練數據品質（驗 unique sample 數、hard neg 品質、contamination）+ 子代理紅隊壓測配置與資料

## 五階段流程（決策級觸發後不可省略）

### ⛔ 藍隊紅隊嚴格分離（lessons learned）

**主進程只能當藍隊。紅隊必須是乾淨子代理。**

理由：

- 主進程已經設計過方案 → confirmation bias 固定在「方案有用」
- 自我紅隊會下意識保護核心假設、攻擊邊角不攻擊根基
- 攻擊力 ~= 乾淨子代理紅隊的 1/10
- 典型模式：自我紅隊找到 0~2 個致命傷，3 個獨立子代理找到 30+ 個

**禁止**：
- 主進程跑「自我紅隊」
- 主進程「想像如果是子代理會怎麼說」
- 用紅隊語氣寫弱化版指控

**允許**：
- 主進程設計藍隊方案
- 主進程派子代理紅隊
- 主進程綜合子代理報告

### 階段 1：CBUA 最佳解（藍隊自我設計）

- C0 路由 → C2 三層思考 → 副作用意識
- 列出至少 3 個替代方案
- 選最佳方案 + 記錄為什麼不選其他
- 預設甜蜜點（最簡可行 + 最少副作用）

### 階段 2：藍隊自我防護

- 列出 5 個可預見的失敗模式
- 對每個失敗模式設計 fallback / guard
- 加上限：token / 數量 / 頻率 / 預算
- 加 provenance / lineage（可追溯）
- ⛔ **不要在這階段「假裝紅隊」**。藍隊只做防護，攻擊留給子代理

### 階段 3：派子代理紅隊（預設 1 個，乾淨子代理）

**預設 1 個紅隊**（涵蓋所有維度）。複雜度超高時升級到 2-3 個分工。

- 預設：綜合型紅隊（架構 + 規範 + 極限全打）
- 升級：Complex/Chaotic + 用戶明確要求「派多個」→ 分工紅隊
  - #1 架構可行性：性能瓶頸、harness 限制、工程成本
  - #2 規範一致性：CBUA / WIREDO / 專案公理違反、認知陷阱
  - #3 極限情境：失敗模式、對抗性場景、災難情境

⛔ **紅隊輪數硬上限 3 輪**（不可違反）：

- 一次設計最多走 3 輪紅隊壓測
- 超過 = 紅隊迴圈 = 設計有根本問題，砍掉重來
- 每輪紅隊修完必須 ship 或砍掉，不能無限改
- 3 輪還沒過 = 方案不該存在（CBUA 第 3 定律「存在質疑」）

每個紅隊 prompt 必須含：
- 完整方案描述
- 上下文約束
- 「找弱點不留情」指示
- 致命級別分類要求

⛔ **派出後驗證子代理真的在跑**（lessons learned）：

- task notification status=completed ≠ 真的有跑
- API overloaded → 0 秒死，但 status 仍顯示 completed
- 必須檢查 output file 大小（0 bytes = 沒跑）
- 0 bytes → 立即重派
- 不能等通知後才發現是空檔

### 階段 4：綜合判決

- ⛔ **必須等齊 N 隊報告才判決**（lessons learned）：
  - 缺一隊 = 階段未完成 = 不能進階段 5
  - 主進程在等期間禁止繼續設計新方案
  - 例外：完全獨立的另一個任務可平行做（不能是同一決策的繼續）
- 收集所有隊報告
- 找共同攻擊點（≥2 隊共識 = 真問題）
- 找獨家盲點（單隊發現也要看）
- 致命反問：「答得出再做」

### 階段 5：修正後執行

- 如果致命傷可修 → 出 vN+1 設計 + 再派一輪紅隊（**總輪數 ≤3**）
- 如果致命傷不可修 → 砍掉重來
- 第 3 輪紅隊仍有致命傷 → 砍掉整個方案，不再派第 4 輪
- 確認過 → 才開始寫代碼
- 寫完 → WIREDO 六維檢查

## 紅隊 prompt 模板

```
你是 Opus 紅隊 #N，專攻 [類型]。
任務：壓測 [方案名] vN，找 [類型] 致命缺陷。

## 待壓測架構
[完整方案描述 + 修正歷史]

## 環境
[harness / 用戶 / 限制]

## 你的任務
從 [N] 個角度全力壓測：
1. [問題 1]
2. ...

提出至少 N 個致命問題 + 修法。
列出最危險的 3 個（會直接讓系統不可用）。
繁體中文，列表形式，找弱點不留情。
```

## 反模式（lessons learned）

- ❌ CBUA 走 C1 直接 ship 架構級決策 → 跳過紅隊
- ❌ 自己想 1 輪就執行 → 跳過紅隊
- ❌ 只派 1 個紅隊 → 蓋章不是壓測
- ❌ 紅隊回來不修就 ship → 紅隊白派
- ❌ 修一輪就 ship → 修完該再派一輪驗證

## 例外（可跳過紅隊）

- Simple 任務（C1 範圍）
- 可逆操作（純讀、實驗腳本、benchmark）
- 已壓測過的同類設計（複用先例）
- 用戶明確說「快」「不用想太多」

## 與其他規則的關係

- CBUA → 提供決策框架（C0~C5）
- ZIQ → 提供公理檢查（單一職責 / 單向流動 / 獨立可驗）
- WIREDO → 提供 ship 前驗證（6 維）
- 紅藍隊 SOP → 把以上 3 個整合成「重大決策」的執行流程
